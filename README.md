# StudentVerifi · EBSU

StudentVerifi is a Flask web application for managing student identity records, generating unique QR credentials, verifying student records, and reviewing verification logs.

## Technology stack

- Python 3.11 or 3.12
- Flask
- SQLAlchemy 2
- Neon PostgreSQL
- Psycopg 3
- HTML, CSS and JavaScript
- `qrcode` for QR image generation
- Vercel for deployment

## Features

- Administrator authentication and password management
- Student records with separate first, middle and last names
- EBSU faculty and department selection
- CSV bulk import with validation
- Unique QR-code generation
- Camera-based and manual QR-token verification
- Active, inactive and invalid verification outcomes
- Student account requests and administrator approval
- Student account access to their own QR code
- Verification history and dashboard statistics
- CSRF protection, password hashing and role-based route access

## EBSU academic catalogue

The application seeds 10 faculties and 59 departments from the university's public Faculties page. The internal database IDs are generated by PostgreSQL and are not official EBSU codes.

Catalogue source: https://ebsu.edu.ng/faculties/

The university's public admission notices may use alternative faculty or department labels in different sessions. For example, the 2026/2027 admission notice groups some medical and engineering units differently from the dedicated Faculties page. The CSV importer includes a limited set of known aliases. Unrecognised labels are rejected for review rather than silently assigned to the wrong faculty.

2026/2027 admission notice: https://ebsu.edu.ng/ebsu-post-utme-approved-cut-off-mark-for-2026-2027-admission-exercise/

## Local setup

1. Install Python 3.11 or 3.12.
2. Create and activate a virtual environment.

   ```bash
   python -m venv .venv
   ```

   Windows PowerShell:

   ```powershell
   .venv\Scripts\Activate.ps1
   ```

   macOS/Linux:

   ```bash
   source .venv/bin/activate
   ```

3. Install the dependencies.

   ```bash
   pip install -r requirements.txt
   ```

4. Copy `.env.example` to `.env`.
5. Set `DATABASE_URL` to your Neon PostgreSQL connection string. Use the pooled connection string if you intend to use Neon's pooler. Ensure the URL includes `sslmode=require`.
6. Set a long, unique `SECRET_KEY`, `INITIAL_ADMIN_USERNAME` and `INITIAL_ADMIN_PASSWORD`.
7. Initialise the database once:

   ```bash
   python -m flask --app app init-db
   ```

8. Start the application:

   ```bash
   python app.py
   ```

9. Open `http://127.0.0.1:5000`, sign in with the initial administrator credentials and change the password.

**Important:** `app.py` no longer creates tables or connects to PostgreSQL when imported. Database setup is a deliberate one-time command. This prevents a database connection from being triggered merely because Vercel imports the Flask application.

For a local-only development setup, the application uses `ChangeMe123!` as the initial administrator password if `INITIAL_ADMIN_PASSWORD` is omitted. Do not rely on this default in any deployed environment.

## Neon PostgreSQL setup

1. Create a PostgreSQL project in Neon.
2. Copy the connection string from the Neon dashboard.
3. Add it to `.env` as `DATABASE_URL`.
4. Run the database initialisation command from your local project folder.
5. Confirm the command reports that the schema and EBSU catalogue have been initialised.
6. Keep the same database connection string in the Vercel environment variables.

Do not commit `.env`, database passwords, or secret keys to GitHub.

This release targets a fresh Neon PostgreSQL database. It does not perform an in-place migration of the previous Aiven MySQL schema. Export authorised student records to CSV and import them into Neon after validating the CSV mapping. Keep the old database unchanged until the new deployment and imported records have been checked.

## Vercel deployment

1. Push the contents of this project folder to the root of the GitHub repository.
2. Import that repository into Vercel.
3. Set the following Production Environment Variables in Vercel:
   - `DATABASE_URL` — Neon PostgreSQL connection string
   - `SECRET_KEY` — long, random secret
   - `INITIAL_ADMIN_USERNAME` — initial administrator username
   - `INITIAL_ADMIN_PASSWORD` — strong initial administrator password
   - `COOKIE_SECURE` — `true`
4. Deploy the project.
5. Open `/health`. A successful database connection returns `{"status":"ok"}`.
6. Sign in with the initial administrator account and change the password.

If the database has not yet been initialised, run `python -m flask --app app init-db` locally with the same Neon `DATABASE_URL` and initial administrator variables. Do not add a public database-initialisation route to the deployed application.

The project includes `public/static/` for Vercel static assets and `static/` for Flask's local static-file handling.

## CSV import format

The preferred CSV header is:

```csv
matric_no,first_name,middle_name,last_name,faculty,department,level,email,status
TEST/2026/000001,Ada,,Example,Faculty of Science,Computer Science,400,ada.example@example.com,Active
```

Required information:
- Matriculation number
- First name
- Surname
- Department
- Level

The faculty may be omitted only when the department uniquely identifies its faculty in the seeded catalogue. The preferred format includes both faculty and department.

The importer accepts separate name columns and also supports a legacy `full_name` column. When only `full_name` is supplied, it interprets the first word as the first name, the final word as the surname, and any intervening words as middle names. Confirm that this ordering matches the source dataset before importing it.

Common alternative headings are recognised, including `matriculation_number`, `registration_number`, `surname`, `faculty_name` and `department_name`.

Import validation includes:
- Matriculation-number syntax and permitted characters
- Required student names and academic details
- Faculty/department consistency
- Duplicate matriculation numbers within the CSV
- Duplicate matriculation numbers already in the database
- Email syntax and status values

The importer uses an all-or-nothing approach: if a row fails validation, no rows from that CSV are imported. Imported records are labelled `imported`; demonstration records are labelled `synthetic`.

The current upload limit is 5 MB. For the approximately 2,500-record dataset, confirm the CSV headers and name ordering against the actual file before the first import.

## Matriculation-number validation

The application normalises matriculation numbers to uppercase and checks for a reasonable length and permitted alphanumeric, slash and hyphen characters. It does not assume one fixed year-specific pattern. This is deliberate because EBSU records published in different contexts show different matriculation-number conventions.

A structurally valid number is not proof that the student is registered. Student account requests are checked against an existing student record, and QR verification checks the token against the database.

## Security and project limitations

- Passwords are stored as hashes.
- Administrator and student routes are role-protected.
- POST forms are protected by CSRF tokens.
- QR codes contain opaque random tokens rather than names or matriculation numbers.
- A copied QR code alone does not prove that the person presenting it is the rightful student. A verifier should also follow an approved identity-checking procedure.
- The sample records are fictional and must not be presented as official EBSU records.
- A real institutional deployment requires authorisation to use student data, appropriate privacy controls, backups, and an identity-verification procedure approved by EBSU.
